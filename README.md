## Технічне завдання

**Назва проєкту:** «TravelManager» – веб-система для комплексного планування,
організації та управління спільними та індивідуальними подорожами.

**Мета розробки:** створення централізованого середовища для планування маршрутів,
логістики, фінансового обліку, розподілу завдань та зберігання документів
(квитків, бронювань) під час подорожей.

---

## Функціональні вимоги

Система повинна реалізовувати наступні функції:

### 1. Керування доступом та ролями

Розмежування прав доступу на рівні кожної подорожі:

- **Організатор** – створює подорож, керує учасниками, має повні права на
  редагування всього маршруту.
- **Учасник** – може додавати власні витрати, відмічати пункти в чеклістах,
  додавати документи та спільні активності.
- **Глядач** – має права виключно на перегляд розкладу та маршруту.

### 2. Управління життєвим циклом подорожі

- **Створення та маршрут:** задання базової інформації (назва, точки
  відправлення/повернення, дати, базова валюта, статус). Додавання конкретних
  міст/країн (TripDestination).
- **Логістика:** облік транспорту (перельоти, потяги) та житла із зазначенням
  статусів бронювання, номерів бронювання та контактних даних.
- **Активності:** планування подій у межах поїздки (екскурсії, зустрічі).
- **Чеклісти:** створення списків завдань або речей для подорожі з можливістю
  відзначати їх виконання.
- **Документи:** завантаження квитків, ваучерів з можливістю їх прямої прив'язки
  до конкретного переїзду, житла або активності.

### 3. Фінансова аналітика та облік (Expense)

- Фіксація витрат із зазначенням категорії, валюти, платника та наявності чеку.
- Можливість прив'язати витрату до конкретного транзиту, житла чи активності.
- Розподіл витрат із фіксацією статусу повернення боргу.

## Опис бази даних

EF Core — Code First. Реляційна база даних, що складається з 16 таблиць.

### Головні сутності

- **User** (IdentityUser): `Id`, `UserName`, `Email`, `CreatedAt`
- **Trip**: `Id`, `Title`, `Description`, `DepartureLocation`, `ReturnLocation`,
  `StartDate`, `EndDate`, `BaseCurrency`, `CreatorId`, `StatusId`, `CreatedAt`
- **TripParticipant**: `TripId`, `UserId`, `RoleId` (складений первинний ключ)
- **TripDestination**: `Id`, `TripId`, `CityName`, `Country`, `Latitude`,
  `Longitude`, `ArrivalDate`, `DepartureDate`
- **Accommodation**: `Id`, `TripId`, `BookingStatusId`, `Name`, `Address`,
  `CheckInTime`, `CheckOutTime`, `BookingReference`, `ContactPhone`,
  `WebsiteUrl`, `Lat/Lon`
- **Transit**: `Id`, `TripId`, `TransitTypeId`, `BookingStatusId`,
  `DepartureLocation`, `ArrivalLocation`, `Times`, `CarrierInfo`,
  `BookingReference`
- **TripActivity**: `Id`, `TripId`, `BookingStatusId`, `Title`, `Address`,
  `StartTime`, `EndTime`, `Notes`
- **Checklist & ChecklistItem**: зв'язка для ведення багажних або організаційних
  списків
- **TripDocument**: `Id`, `TripId`, `FileName`, `FilePath`, `UploadedAt` + FK на
  `Transit`, `Accommodation`, `TripActivity`

### Фінансовий блок

- **Expense**: `Id`, `TripId`, `CategoryId`, `Title`, `TotalAmount`, `Currency`,
  `Date`, `PayerId`, `ReceiptImageUrl` + FK на `Transit`, `Accommodation`,
  `TripActivity`
- **ExpenseSplit**: `Id`, `ExpenseId`, `DebtorId`, `OwedAmount`, `IsSettled`

### Довідники

- **TripRole**: Organizer, Participant, Viewer
- **TripStatus**: Planned, In Progress, Completed, Cancelled
- **BookingStatus**: Not Booked, Pending, Confirmed, Cancelled
- **ExpenseCategory**: Accommodation, Transport, Food, Entertainment, Shopping,
  Other
- **TransitType**: Flight, Train, Bus, Car, Ferry, Other

  проживання (готелів).
- **BookingStatus — Accommodation** – 1:N, бо один статус бронювання може мати
  багато готелів.
- **Trip — Transit** – 1:N, бо одна подорож може мати кілька переїздів чи
  перельотів.
- **TransitType — Transit** – 1:N, бо один тип транспорту стосується багатьох
  квитків.
- **BookingStatus — Transit** – 1:N, бо один статус бронювання може стосуватися

- **Trip — TripActivity** – 1:N, бо одна подорож може містити багато

  стосуватися багатьох активностей.
- **Trip — Expense** – 1:N, бо в одній подорожі може бути багато різних витрат

# Робота з API

## Сценарій інтеграції

**Назва:** деталі подорожі
**Проблема користувача:** користувач додає місто до маршруту поїздки, але не має швидкого доступу до актуальної інформації — яка погода на місці, яка валюта країни, який курс обміну, де знаходиться готель на карті.  
**Рішення:** сторінка `/TripDestinations/Info/{id}` агрегує локальні дані з БД та три зовнішніх API в єдину туристичну картку міста. Також при додаванні міста або готелю координати визначаються автоматично через Nominatim.

### Потік даних

```
BД (Accommodation.Address або TripDestination.CityName)
        ↓
Nominatim API → Latitude, Longitude (геокодування адреси/міста)
        ↓
БД (збереження координат) → Відображення на карті
```

```
БД (TripDestination.CityName, Country, Latitude, Longitude)
        ↓
Open-Meteo API      → Поточна погода + 3-денний прогноз (за координатами)
REST Countries API  → Прапор, мови, столиця, населення, валюта (за назвою країни)
НБУ API             → Курс EUR, USD та валюти країни до UAH
        ↓
Відображення на сторінці деталей
```

## Fallback-стратегії

Кожен сервіс обгорнутий у `try/catch` і повертає `null` або порожній список при помилці. `DestinationInfoService` запускає всі три API **паралельно** через `Task.WhenAll` — збій одного не зупиняє інших.

| API недоступний | Поведінка застосунку |
|----------------|---------------------|
| Open-Meteo | `WeatherAvailable = false` → View показує блок "Погода тимчасово недоступна" |
| REST Countries | `CountryAvailable = false` → View показує блок "Інфо про країну недоступне" |
| НБУ | `ExchangeRatesAvailable = false` → View показує блок "Курси валют недоступні" |
| Nominatim | `null` → координати не зберігаються, місто буде без маркера на карті |

## Як запустити

1. Клонувати репозиторій
2. Скопіювати шаблон: `appsettings.Development.json.example` → `appsettings.Development.json`
3. Налаштувати рядок підключення до БД в `appsettings.json`
4. Виконати міграції: `dotnet ef database update`
5. Запустити: `dotnet run` або F5 у Visual Studio
6. Swagger доступний за адресою: `https://localhost:{port}/swagger`
7. Туристична картка: `https://localhost:{port}/TripDestinations/Info/{id}`


### Як працює система запрошень

1. Організатор вводить email учасника та вибирає роль
2. `TripsController.InviteParticipant()` перевіряє чи email вже зареєстрований
3. Якщо так — одразу додає `TripParticipant` до бази та надсилає email через `IEmailService` (SMTP)
4. Якщо ні — формує посилання `/Account/Register?tripId=5&email=xxx&roleId=2` та надсилає на email
5. Новий користувач реєструється → автоматично додається до подорожі з заданою роллю

### Як реалізована безпека

- Всі контролери мають атрибут `[Authorize]` — неавторизовані перенаправляються на логін
- Перевірка належності до подорожі: кожен action перевіряє `TripParticipant` для поточного userId
- Перевірка ролі: дії що модифікують дані перевіряють `role.Name != "Viewer"`
- CSRF захист: всі POST-форми мають `@Html.AntiForgeryToken()` + `[ValidateAntiForgeryToken]`
- Google OAuth: секрети зберігаються в `appsettings.json` (не в коді)
- Pexels API key не передається на клієнт — тільки через серверний проксі

# Фінальний проєкт

### 1. Інтеграція штучного інтелекту та геопросторових сервісів
Для автоматизації надання туристичної інформації на сторінці деталізації пунктів призначення (`TripDestinations/Info/{id}`) було реалізовано інтелектуальний конвеєр (Pipeline) обробки даних на основі великих мовних моделей та геолокаційних сервісів.

* **Контекстуальний AI за допомогою Groq Cloud API (Llama 3.3 70b):** Замість генерації абстрактних або вигаданих (галлюцинованих) порад, сервіс `AiRecommendationService` використовує комбінований підхід. Спочатку система звертається до **Foursquare Places API**, отримуючи реальні локації інтересу (POI), ресторани та пам'ятки з їхніми дійсними рейтингами. Цей список передається як структурований контекст у системний промпт до LLM. Модель Groq аналізує дані та повертає гнучкий, локалізований українською мовою звіт у форматі JSON з детальними рекомендаціями для мандрівника.
* **Інтерактивна картографія (Leaflet.js):** При додаванні міста чи готелю вбудований `NominatimService` (OpenStreetMap) автоматично геокодує текстову адресу у географічні координати `Latitude` та `Longitude`, визначаючи також назву країни англійською мовою (для сумісності з REST Countries API). На фронтенді за допомогою JS-бібліотеки **Leaflet.js** динамічно будується інтерактивна карта з маркерами логістичних точок подорожі.

### 2. Модуль чеклістів та шаблонізації
Для полегшення зборів перед поїздкою спроєктовано та реалізовано підсистему шаблонів чеклістів. База даних доповнена таблицями `ChecklistTemplates` та `ChecklistTemplateItems`.
* Впроваджено **4 базових системних шаблони** збирання речей: *Базовий пакувальний, Пляжна відпустка, Бізнес-поїздка, Гірський похід*.
* Користувач одним кліком може застосувати обраний шаблон до своєї поїздки. При цьому бізнес-логіка на бекенді здійснює глибоке копіювання елементів з таблиці шаблонів у нові екземпляри сутностей `Checklist` та `ChecklistItem` з прив'язкою до конкретної `TripId`. Зміна та відмітка статусів виконання елементів здійснюється асинхронно через AJAX-запити за допомогою Fetch API.

### 3. Модуль фінансового клірингу та експорту аналітики (EPPlus 8)
Одним із найскладніших модулів проєкту є підсистема автоматичного врегулювання спільних витрат групи користувачів.
* **Алгоритм мінімізації транзакцій (Greedy Debt Settlement):** Коли один учасник створює запис у таблиці `Expenses`, система автоматично розраховує частки обраних боржників та зберігає записи у `ExpenseSplits`. Після завершення подорожі застосовується «жадібний» фінансовий алгоритм клірингу. Він збирає сумарні баланси кожного учасника (хто в мінусі, хто в плюсі), сортує їх за величиною відхилення та ітеративно покриває найбільші борги за рахунок найбільших кредитів. Це дозволяє звести взаєморозрахунки до мінімально можливої кількості грошових переказів між людьми.
* **Генерація трьохсторінкових Excel-звітів:** За допомогою бібліотеки **EPPlus 8** реалізовано експорт фінансових результатів у форматі `.xlsx`:
    * *Аркуш 1 (Витрати):* Повна таблиця витрат із можливістю фільтрації за учасниками, категоріями та автоматичним підбиттям підсумків.
    * *Аркуш 2 (Борги):* Детальний перелік усіх розподілів (Splits) з кольоровим умовним форматуванням статусів (Погашено / Актуальний борг).
    * *Аркуш 3 (Взаєморозрахунки):* Фінальний баланс кожного учасника та згенерований алгоритмом покроковий мінімальний план виплат.

### 4. Надійність, відмовостійкість (Resilience) та кешування
Оскільки сторінка деталей залежить від стабільності 5 сторонніх сервісів, у файлі `Program.cs` було реалізовано патерни стійкості:
* **Polly Resilience Handler:** Для кожного іменованого HTTP-клієнта налаштовано `AddStandardResilienceHandler`. Він реалізує стратегію автоматичних повторних запитів (Retry) із експоненціальним збільшенням затримки (Exponential Backoff) та автоматичний вимикач мережі (Circuit-Breaker). Якщо зовнішній API (наприклад, REST Countries) виходить з ладу, система не "падає", а активує Fallback-стратегію: інтерфейс приховує дефектний блок або підставляє локальну заглушку, продовжуючи стабільну роботу.
* **Оптимізація запитів через IMemoryCache:** З метою зниження навантаження на сторонні сервіси та запобігання блокуванню за лімітами запитів (Rate Limiting), відповіді зовнішніх API кешуються в оперативній пам'яті сервера:
    * Прогноз погоди Open-Meteo — на 10 хвилин.
    * AI-рекомендації Groq та дані країн — на 6 годин.
    * Курси валют НБУ — до кінця поточної доби.


## 4. Повний стек технологій та архітектурна структура
За результатами завершення всіх етапів розробки веб-система «TravelManager» є повністю працездатним MVP (Minimum Viable Product). Система успішно розділена на 4 ізольованих шари відповідно до Clean Architecture:

1.  **TravelManager.Domain:** Чисті сутності БД (`Trip`, `User`, `Expense`, `Checklist` тощо), константи та Enums. Нуль зовнішніх інфраструктурних залежностей.
2.  **TravelManager.Application:** Об'єкти передачі даних (DTOs) для десеріалізації відповідей сторонніх інтеграцій.
3.  **TravelManager.Infrastructure:** `ApplicationDbContext` (успадкований від `IdentityDbContext<User>`), міграції, реалізація інтерфейсів репозиторіїв та бізнес-сервісів (AI, Email, Курси валют).
4.  **TravelManager.UI:** Контролери MVC, Razor-представлення (`.cshtml`), валідатори FluentValidation, конфігурація `Program.cs`. Стилізація виконана за допомогою утилітарного CSS-фреймворку **Tailwind CSS 4** (з ефектами Glassmorphic та 3D-нахилом елементів за допомогою `Tilt.js`).

## 5. Комплексна система безпеки та авторизації
* **ASP.NET Core Identity & Google OAuth 2.0:** Реалізовано подвійну модель входу (класична пара email/пароль + швидка авторизація через Google-акаунт). Для локальної форми автентифікації підключено кастомний клас `UkrainianIdentityErrorDescriber`, що забезпечує повну українізацію системних повідомлень про помилки паролів або валідації.
* **Захист від CSRF/XSS:** Усі форми модифікації даних захищені атрибутами `[ValidateAntiForgeryToken]` та відповідними сервісними токенами в Razor. Всі контролери, крім публічного API, закриті глобальним атрибутом `[Authorize]`.
* **Серверний проксі-сервер (Pexels API Proxy):** Для динамічного підвантаження відео- та фото-фонів міст було виявлено загрозу безпеці: передача API-ключа Pexels безпосередньо у фронтенд-скриптах відкриває його для викрадення. Було розроблено серверний проксі-ендпоінт всередині `PexelsProxyController`. Клієнтський браузер надсилає запит на внутрішню адресу програми, сервер зчитує секретний токен із захищеного `appsettings.json`, сам звертається до Pexels, а клієнту повертає лише безпечний результат.
